# Шаблон Release Notes

## Общие принципы

Формат: .md
Tone of Voice: деловой, технический, ориентированный на пользователя
Язык: русский
Нумерация разделов: не нужна
Маркеры: ● (основной уровень), ○ (второй уровень)

## Структура документа

### Начальное описание

*Общее описание Release Notes зависит от того, мажорный релиз или патч.*

Примеры описаний:
- Мажорный релиз: «Этот релиз сфокусирован на оптимизации работы продукта, улучшении UI/UX и интеграции с еще большим количеством ведущих инструментов безопасности.»
- Патч: «Этот релиз сфокусирован на повышении стабильности и качества системы.»

### Сводка

Группировка по типам изменений:

● Добавлены новые возможности:
 ○ [Название возможности 1]
 ○ [Название возможности 2]
 ○ [Название возможности N]

● Исправлены следующие проблемы:
 ○ [Описание проблемы 1]
 ○ [Описание проблемы 2]
 ○ [Описание проблемы N]

Примечание: если релиз содержит только одну категорию (например, только исправления), перечислять в плоском списке с маркером «●».

### Что нового

Каждая фича оформляется как отдельный подраздел.

Формат:

[Название фичи / заголовок] — [Техническое описание — что реализовано, для чего, контекст] — [Что изменилось для пользователя — Описание UX-изменений: что теперь видит/может делать пользователь]

Пример:

Возможность запуска CLI-инструментов через k8s — Поддержка запуска CLI-инструментов, таких как Semgrep, PVS-Studio, Trivy и т.д.,
в виде динамических подов в Kubernetes — Что изменилось для пользователя: Пользователи могут настраивать запуск CLI-инструментов с помощью YAML-шаблонов в интерфейсе системы и использовать специальные плейсхолдеры для настройки. Данный способ запуска доступен только при развертывании в Kubernetes.

### Новые интеграции [опционально]

Описание интеграций с внешними системами. Структура аналогична разделу «Что нового».

### Исправления [опционально]

Требуется, если релиз содержит багфиксы, хотфиксы и пр.

Формат:

[Краткое описание проблемы — заголовок] — [Развернутое описание: что было не так, что исправлено]

Пример:

Ошибка сохранения новых API-токенов при редактировании инструмента или источника — Исправлена ошибка, при которой новые API-токены не сохранялись в ходе редактировании инструмента или источника

### Изменения в REST API

#### Новые эндпоинты

Формат:

[Эндпоинт] — [Метод] — [Описание]

#### Измененные эндпоинты

Формат:

[Эндпоинт] — [Было] — [Стало]

#### Удаленные эндпоинты

Формат:

[Эндпоинт] — [Причина удаления]

## Правила стиля

1. Заголовки фич/исправлений — начинается с существительного, а не с глагола (не «Добавили ...», а «Поддержка ...», «Возможность ...»). Точка на конце заголовков не ставится.
2. Описание — технически точное, но доступное для пользователя. Без сленга.
3. Что изменилось для пользователя — описание в повествовательном стиле, с фокусом на действиях пользователя (например, «Пользователи могут...», «Можно сравнивать ...», «Теперь доступна возможность...»).
4. Маркеры — ● для основного уровля, ○ для вложенного уровня.
5. Пунктуация в списках — точка с запятой (;) у внутренних пунктов, точка (.) в конце последнего.
6. Release Notes — всегда в Title Case в заголовке.
